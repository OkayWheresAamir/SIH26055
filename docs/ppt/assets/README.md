# Slide assets — paste these into PowerPoint

Nine pictures, each cropped tight with no title, frame or caption, so you can place
and label them yourself. Regenerate all of them with:

```bash
python docs/ppt/figures/mk_assets.py
```

**Every one is measured output from this project, not an illustration.** Sources are
`config_2.h5` (a real Turing stare recording) and one `ScanEnv` episode driven by the
rung-17c checkpoint, both read on 2026-09-20.

| File | What it shows | Where it came from | Suggested use |
|---|---|---|---|
| `spectrum_bars.png` | 36 bands, bar height = how busy each one really was; red outline = the ±500 MHz the receiver hears at once | `Z.mean(axis=1)` over the real truth grid | Flow A, the strip that sets up the problem |
| `pulse_cloud.png` | Every recorded pulse — time across, frequency up, colour = power | 14,000 of the 644,674 real PDWs in `config_2.h5` | Flow B, "recorded radar" |
| `beam_lobes.png` | One emitter's power over 30 s; each peak is its beam sweeping across us | loudest pulse per 0.1 s for the emitter with the largest real amplitude swing | Flow B, "group pulses by emitter" — the clearest picture of a *spatially scanning* emitter |
| `occupancy_grid.png` | The band–slot grid, cropped so single cells are visible. One cell = one band for one 50 ms slot | real `TruthGrid.Z`, slots 210–270 | Flow B, "fill the 36 × 600 grid" |
| `detection_curve.png` | Chance of declaring a hit against how loud the signal is; dashed line = the threshold | `Φ((S−γ)/σ)` at the frozen σ = 3 dB | Flow B, beside the receiver decision |
| `obs_heatmap.png` | What the scheduler remembers: 5 numbers × 36 bands. Rows are hit rate, airtime share, staleness, current band, hit streak | one live 183-value observation, mid-episode | Flow C, "183 numbers from its own scan history" |
| `band_distribution.png` | The policy's actual output — a weight on every band, favourite in red | rung-17c softmax at that step; max 0.115, entropy 3.199 against ln 36 = 3.584 | Flow C, "a weight on all 36 bands" |
| `waterfall_strip.png` | A whole 30 s episode: grey = a band genuinely transmitting, red = where we pointed | real `ScanEnv` episode (ratio 0.1436, 2.51 s, coverage 0.947 on this scenario) | Slide 3 or 5 — the "working prototype" picture |
| `band_ladder.png` | The 36 bands as a stack, with the tuned one lit | schematic | Flow A, "point at one band" |

## Two things to keep if you relabel them

- `obs_heatmap.png` is **wider than what produced it** — one bit comes back about one
  band, but all 36 columns update. That is the point of the picture.
- `band_distribution.png` has **no single dominant bar** on purpose. The policy has not
  collapsed, and that is correct behaviour, not indecision.
